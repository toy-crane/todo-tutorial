# commit

사용자의 작업을 하나의 깔끔한 커밋으로 남기는 절차다. 목표는 "이번 작업만, 이 저장소의 방식대로" 커밋하는 것이다. 관련 없는 파일이 섞이거나 메시지 형식이 제각각이면 나중에 히스토리를 읽고 되돌리기가 어려워진다.

## 1. 바뀐 파일과 diff 확인

다음을 실행해 현재 상태를 파악한다.

```bash
git status
git diff            # 아직 스테이징 안 된 변경
git diff --staged   # 이미 스테이징된 변경
```

- 새로 생긴(untracked) 파일은 diff에 안 나오므로 `git status`에서 따로 확인하고, 필요하면 내용을 열어 본다.
- 변경 사항이 아예 없으면 커밋하지 말고 "커밋할 변경이 없다"고 알린다.

## 2. 이번 작업과 관련된 파일만 스테이징

대화에서 사용자와 함께 한 작업이 무엇인지 기준으로, 그 작업에 속하는 파일만 고른다.

- `git add -A`나 `git add .`는 쓰지 않는다. 관련 없는 실험 파일, 로컬 설정, 비밀값(`.env` 등)이 같이 들어갈 수 있기 때문이다. 파일 경로를 하나씩 지정해 `git add <path>`로 스테이징한다.
- 이번 작업과 무관해 보이는 변경이 있으면 스테이징하지 않고, 커밋 후 "이 파일들은 관련이 없어 보여 제외했다"고 목록을 알려 준다.
- 어느 쪽인지 정말 판단이 안 서는 파일이 있으면 커밋 전에 사용자에게 묻는다.
- 이미 스테이징된 파일 중 관련 없는 것이 있으면 `git restore --staged <path>`로 빼고 그 사실을 알린다.

스테이징 후 `git diff --staged --stat`으로 의도한 파일만 들어갔는지 한 번 더 확인한다.

## 3. 최근 커밋과 같은 형식으로 메시지 작성

형식을 짐작하지 말고 저장소의 실제 기록을 본다.

```bash
git log -10 --format='%s%n%b---'
```

여기서 다음을 따라 한다.

- **접두어 규칙**: 예를 들어 `feat:`, `fix:`, `docs:`, `test:`처럼 타입을 붙이는지, `docs(readme):`처럼 scope를 쓰는지.
- **언어**: 최근 커밋이 한국어면 한국어로 쓴다.
- **어조와 길이**: "~ 추가", "~ 구현"처럼 명사형으로 끝나는지, 한 줄로 끝나는지, 본문을 쓰는지.

메시지는 "무엇을 했는지"보다 "무엇이 바뀌었는지"가 한눈에 보이게 짧게 쓴다. 변경이 여러 성격(기능 + 테스트 등)을 섞고 있다면 대표하는 타입 하나를 고르고, 정말 성격이 다른 작업이 섞였다면 커밋을 나누자고 제안한다.

시스템이나 사용자 지침에 커밋 메시지 끝에 붙일 문구(예: `Co-Authored-By:`)가 정해져 있으면 그대로 붙인다.

여러 줄 메시지는 HEREDOC으로 넘겨 줄바꿈이 깨지지 않게 한다.

```bash
git commit -m "$(cat <<'EOF'
feat: 할 일 우선순위 추가

Co-Authored-By: ...
EOF
)"
```

## 4. 결과 확인과 보고

```bash
git status
git log -1 --stat
```

사용자에게 다음을 짧게 알린다.

- 커밋 메시지
- 커밋에 포함된 파일
- 제외한 파일이 있으면 그 목록과 이유

pre-commit 훅 등으로 커밋이 실패하면 원인을 고친 뒤 **새로** 커밋한다. 사용자가 요청하지 않았다면 `--amend`, `--no-verify`, `push`는 하지 않는다 — 이미 있는 커밋을 바꾸거나 검사를 건너뛰거나 원격에 올리는 건 사용자가 직접 결정할 일이기 때문이다.
